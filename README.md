# GitHub 取得（github-fetch）

GitHub で起きたこと（PR・レビュー・コメント・コミット・issue）を、**読むだけで、抜けなく**手元にためる仕組みです。毎朝の自動取得と、状態を見る Mac のメニューバーのアプリが付いています。

GitHub の公式の道具 `gh` で、REST API の読み取り（GET）だけを使います。AI は使いません。決まった手順で取って、数えて、照合するので、毎回同じ結果になり、費用もかかりません。

- **GitHub に書き込まない**: コメント・ラベル・マージ・push など、GitHub に書き込むことはしません。gh のログインは書き込みもできる広さですが、問い合わせはすべて1つの関数を通し、`gh api --method GET` と決めた場所だけを通します（許可リスト）。許可の外は、その回を止めて取得ログに全文を残します
- **主役は「基準のブランチに入ったもの」**: PR を通ったものも、PR を通らずに直接 push されたものも、ブランチに入った時刻で、日本時間の日ごとに数えます。PR 経由は PR 1 件で 1 つ、直接はコミット 1 つずつです
- **毎回照合する**: GitHub 自身の数（基準のブランチの先頭・開いている PR と issue の数・検索の件数・PR と issue に起きた出来事）と、取ったものを突き合わせます。合わなければ NG で知らせ、次の回で取り直します。「0件（該当なし）」と「取れなかった」は、別の言葉で出します。最後まで読めなかったリポジトリは「OK」と言わず、「確かめていない」と理由を出します
- **使いすぎない**: 1回の取得で GitHub に問い合わせてよい回数（既定 1,500 回）を超えたら止まり、次の回が続きから取ります。変わっていないものは、回数を使わない問い合わせ（304）で済ませます
- **ソースコードの中身は取らない**: ファイルの中身・差分は、保存する前に捨てます。clone もしません

## 使う前に（必ず読んでください）

これは個人が作った道具で、GitHub の公式のものではありません。使う前に、次の3つを確かめてください。

- **会社の GitHub で使うなら、先に会社の決まりを確かめる**: 組織のリポジトリの PR・issue・コメントは、会社のデータです。それを自分の Mac にためることになります。組織の設定によっては、gh から組織のリポジトリが見えません（シングルサインオン〈SSO〉の許可が要る・組織が gh のようなアプリを制限している、など）
- **GitHub の決まりを守るのは、使う人**: この仕組みは、自分の Mac で、自分の GitHub のログインのまま、自分が見られるリポジトリを自分の手元にためるためのものです。ログインを人と共有したり、ほかの人に向けたサービスにしたりしないでください（関係する決まりは「気をつけること」）
- **ある日、動かなくなることがある**: GitHub の API や gh の変更しだいで、返ってくる形が変わることがあります。そのときは照合で止まります（黙って間違えはしません）。取った原本は、そのまま残ります

## そろえるもの

| もの | 中身 |
| --- | --- |
| Mac | macOS 14 以上（試したのは macOS 26） |
| Mac の開発用の道具 | ターミナルで `xcode-select --install`（無料）。Xcode が入っていれば不要。python3（Mac に付いてくる 3.9 で動きます。足す部品はありません）とアプリの組み立てに使います |
| gh（GitHub CLI） | GitHub の公式の道具。ターミナルで `brew install gh`。Homebrew を使っていなければ [GitHub CLI](https://cli.github.com/) から入れます |
| GitHub のアカウント | 取りたいリポジトリが見えるアカウント。gh へのログインは、アプリの「はじめの準備」が案内します |
| 日本時間 | 日付を日本時間で区切ります。ほかの時間帯では試していません |

Claude Code は要りません。Cursor・VS Code で Claude Code を使っているなら、準備を手伝ってもらえます（下の「はじめ方」）。

## はじめ方

1. **取ってくる**: このページの「Code」→「Download ZIP」で取ってきて展開し、できたフォルダを**ホームの直下**（例: `~/github-fetch`）に置きます（`git clone` でもかまいません。フォルダの名前は何でもかまいません）
   - 「書類」「ダウンロード」「デスクトップ」の中にも置けますが、その場合はアプリがフォルダを読む許可を求めてきます（許可すれば使えます）
   - 取ったデータは、このフォルダとは別に、ホームの直下の `~/GitHub取得データ` に入ります（下の「できるもの」）。このフォルダを新しい版に入れ替えても、取ったデータは消えません
2. **組み立てる**: ターミナルで、そのフォルダに入って次の1行を動かします（15〜20秒）。最後に「できました」と出れば成功です

   ```bash
   cd ~/github-fetch
   bash アプリ/build.sh
   ```

   - Cursor か VS Code で Claude Code を使っているなら、このフォルダを開いて「準備して」と頼むと、Claude が `CLAUDE.md` の手順で、開発用の道具と gh の確認・リンクの調べ直し・組み立てまで手伝います
3. **アプリを開く**: Finder で `アプリ/build/GitHub取得.app` をダブルクリックします。「はじめの準備」の窓が出るので、案内どおりに進めます
   - **① GitHub にログインする**: 「ターミナルでログインを始める」を押すと、ログインの準備をしたターミナルの窓が開きます（中身は `gh auth login --web`）。ブラウザで、ターミナルに出た8文字のコードを入れて「Authorize」を押します。アプリに戻って「ログインを確かめる」を押すと、アプリが本当に GitHub を読めるかを確かめて、見えるリポジトリの一覧を読みます（数秒）
   - **② 取るリポジトリを選ぶ**: 一覧から、取りたいリポジトリにチェックを付けます（いくつでも）。名前の一部を入れると絞り込めます。ほかの人の公開リポジトリは、`owner/name`（例: `ggml-org/whisper.cpp`）を入れて Enter で探します。リポジトリごとに、呼び名（2〜4文字）・基準のブランチ（入ったものを数えるブランチ。ふつうは既定のブランチ）・取り始める日を決めます。取り始める日の既定は、リポジトリを作った日（全部）です。最初の取得の見込みが 1,500 回を超える大きいリポジトリは、はじめから「90日前から」を選んでおきます。見込みは、チェックを付けたあと数秒で届きます。届いたときに、まだ取り始める日を変えていなければ、大きいリポジトリは「90日前から」に切り替わります。どちらを選んでも、見込みの回数と、何回に分けて取るかが出ます。「保存して次へ」を押すまでは、何も保存されません
   - **③ 取得を始める**: 「最初の取得を始める」を押します。取り始める日からの分をまとめて取ります。大きいリポジトリは、1回の上限（1,500 回）で止まり、アプリは黄色で「最初の取得の途中です」と出します。もう一度「今すぐ取る」を押すか、次の朝の自動取得で、続きから取ります（何回かに分かれます）。最後まで取るまでは、照合は「確かめていない」になります
   - 「毎朝 9:00 に自動で取る」は、はじめからオンです（最初の取得のあとから動きます。時刻は歯車で変えられます）。自動の取得には、このアプリが開いている必要があるので、③ の画面か歯車で「Mac の起動時にこのアプリを開く」もオンにしておきます。Mac がスリープしていた日は、点検のために一瞬起きたときか、Mac が起きたときに始めます。途中のスリープで取れなかった分があるときは、アプリが黄色で知らせるので、Mac が起きているときに「もう一度取る」を押してください
   - アプリは「アプリケーション」フォルダに移してもかまいません。取得の仕組みのフォルダは、組み立てたときの場所を覚えています
   - あとでフォルダを動かしたり名前を変えたりしても、同じ Mac の中なら、アプリが自動で追いかけて「移動していました」と知らせます。見つからないとき（ゴミ箱に入れた・外付けのディスクへ移したなど）は、アラートの「場所を選ぶ」か、設定の「取得の仕組みのフォルダ」で選び直してください。見つかるまで、取得はしません
4. **ターミナルで取ることもできます**: 次の1行を動かします。最後に照合の結果が出ます

   ```bash
   cd ~/github-fetch
   caffeinate -i python3 github.py fetch
   ```

   - `caffeinate -i` は、取得の途中で Mac が眠らないようにするためのものです。ただし、電池で動いているときは、ふたを閉じると眠ります（取得も止まります。次は続きから取ります）。大きいリポジトリを取るときは、電源につないでおくと安心です

### 自分の手で始めるとき（ターミナルだけで）

1. 上と同じように取ってきて、ホームの直下に置きます
2. gh にログインします: `gh auth login`（ブラウザで進める形をおすすめします）。`python3 github.py setup --login` で、取る係が GitHub を読めるかを確かめられます
3. 取るリポジトリを書きます

   ```bash
   cd ~/github-fetch
   mkdir -p ~/GitHub取得データ
   cp リポジトリ.例.json ~/GitHub取得データ/リポジトリ.json
   ```

   `~/GitHub取得データ/リポジトリ.json` には、1リポジトリを1行で書きます。例の 2 行は、自分の取りたいリポジトリに書き換えてください（2 行目の番号は 0 なので、そのままだと「番号が入っていない」と止まります。1 行目の whisper.cpp を残すと、最初の取得で約 650 回使います）

   | 欄 | 中身 |
   | --- | --- |
   | `id` | リポジトリの番号（GitHub の ID）。`python3 github.py setup --find owner/name` で調べると、`~/GitHub取得データ/リポジトリ候補.json` に出ます |
   | `name` | `owner/name` |
   | `tag` | 短い呼び名（2〜4文字）。アプリの表示に使います |
   | `base` | 基準のブランチ（入ったものを数えるブランチ。ふつうは既定のブランチ） |
   | `from` | 取り始める日（`YYYY-MM-DD`。日本時間）。ふつうはリポジトリを作った日。`python3 github.py setup --inspect owner/name` を動かすと、作った日（`created`）と最初の取得の見込みの回数（`estimate` の全部・90 日前から）が `~/GitHub取得データ/リポジトリ候補.json` に書かれます |
   | `stages` | 空のまま `[]` にしておきます（確認環境・本番のブランチの届き具合は、まだ作っていません） |
   | `added` | 足した日（`YYYY-MM-DD`） |

4. 最初の取得: `caffeinate -i python3 github.py fetch`（上の4と同じ）。1回の上限で止まったら、同じ1行をもう一度動かせば続きから取ります
5. アプリ: `bash アプリ/build.sh` で組み立てて、Finder から開きます（`~/GitHub取得データ/リポジトリ.json` があれば、はじめの準備の窓は出ません）

取れるのは、自分の GitHub のアカウントから見えるリポジトリ（公開リポジトリと、権限のある非公開リポジトリ）です。

## リポジトリを足す・外す

メニューの「GitHub とリポジトリ…」（または歯車 →「取るリポジトリ」の「開く…」）で、はじめの準備と同じ窓が、リポジトリの画面から開きます。

- 足す・外す・呼び名や基準のブランチ・取り始める日を変えることができます。**「保存する」を押すまでは、何も変わりません**
- 取り始める日を前にずらすと、足りない古い分を足して取ります（取ってある所は取り直しません。大きく足すと、最初の取得と同じく何回かに分かれます）。後ろにずらしても、取ったデータは消えません
- 基準のブランチを変えると、新しいブランチの入った記録を取り始める日から取り、入ったものを新しいブランチで数え直します（過去の日の棒が変わります）
- **外したリポジトリの取ったデータは消えません**。状況ページの数と照合に使わなくなるだけです
- 外したリポジトリは「前に取っていたリポジトリ」に出ます。付け直すと、前の呼び名・基準のブランチ・取り始める日に戻ります。前に取った分は使い回して、取っていない期間（外していた間）と最近の分だけを取ります
- 足したリポジトリは、次の取得（「今すぐ取る」か毎朝の自動取得）で、取り始める日からの分をまとめて取ります

## 新しい版にするとき

取ったデータは、取得の仕組みのフォルダ（このフォルダ）の外の `~/GitHub取得データ` にあります。仕組みのフォルダは、新しい版にまるごと入れ替えてかまいません。

1. 新しい版を取ってきます（「Download ZIP」で取ってきて展開する。`git clone` した人は、そのフォルダで `git pull`）
2. 前のフォルダと入れ替えます（別の場所に置いてもかまいません）
3. 新しいフォルダで `bash アプリ/build.sh` を動かして、アプリを組み立て直します（「アプリケーション」フォルダに入れている人は、入れ直します）
4. アプリを開きます。別の場所で組み立て直したときは、アプリがそちら（新しい版）を使います

## できるもの

取ったものは、すべてホームの直下の `~/GitHub取得データ/` に入ります。取得の仕組みのフォルダ（このフォルダ）の外に置くのは、仕組みを新しい版に入れ替えても消えないように、また、このフォルダを GitHub などに上げても取ったデータが混ざらないようにするためです。

```text
~/GitHub取得データ/
├─ リポジトリ.json                         取るリポジトリ（アプリの「はじめの準備」で選ぶか、自分で書く）
├─ 外したリポジトリ.json                   一覧から外したリポジトリの呼び名・基準・取り始める日（付け直すと戻す）
├─ リポジトリ候補.json                     はじめの準備で GitHub から読んだリポジトリの一覧（アプリが読む）
├─ 状態.json・取得の記録.jsonl・例外.json    いまの状態と、毎回の取得の結果（アプリが読む）
├─ リポジトリ/
│   ├─ ggml-org__whisper.cpp__541269386/   1リポジトリ1フォルダ（owner__name__ID）
│   │   ├─ 原本/pulls/2026-10/ …          GitHub から返ってきたそのまま（1ページ1ファイル・種類ごと・取った月ごと）
│   │   ├─ 記録/                          入ったもの・PR・issue・コメント・出来事・CI・リリース（1件1行。下の表）
│   │   └─ しおり.json                    前回の続き（どこまで取ったか・変わっていないかの印）
│   └─ …（リポジトリの数だけ）
└─ 取得ログ/2026-10/ …                     毎回のログの全文と、問い合わせ1回ごとの1行（月ごと）
```

- リポジトリの名前があとで変わっても、番号（ID）で見分けるので困りません（フォルダの名前は最初の名前のまま。照合の注記で「名前が変わっていました」と知らせます）
- 取ったデータは、iCloud（「書類」「デスクトップ」の同期）や Google ドライブで同期される場所へは動かさないでください。会社のリポジトリのデータが、個人のクラウドに上がります

### 残すもの・消してよいもの

バックアップするなら、`~/GitHub取得データ/` を丸ごと写してください。

- 消してよいのは、次の3つだけです
  - `記録/`（取るたびに、原本から作り直します。`python3 github.py build` でも作り直せます）
  - `リポジトリ候補.json`（はじめの準備で読み直せます）
  - 古い取得ログ（`取得ログ/` の、前の月のフォルダ）
- ほかは消さないでください
  - `原本/` は、GitHub から返ってきたそのままのもので、手元では作り直せません。CI の結果は約 13 か月で GitHub から消えます。あとから書き直されたり消されたりしたコメントも、取り直しても前の形には戻りません。「いつ知ったか」（下の `known_at`）も、原本の取った時刻から作っています
  - `しおり.json` を消すと、次の取得は、そのリポジトリを取り始める日から取り直します（抜けはしませんが、最初の取得と同じくらい回数を使います）

`記録/` には、1件を1行で書きます（JSONL）。時刻は UTC（末尾の `Z`）で、日に分けるときだけ日本時間にします。

| ファイル | 中身 |
| --- | --- |
| `入ったもの.jsonl` | 基準のブランチに入ったコミット。入った時刻（`landed_at`）・入り方（`landed_by`: `pr_merge`・`push`・`branch_creation`・`force_push` など）・PR 経由なら PR の番号（`via_pr`）・マージのコミットか（`merge`。数えない）・強制の書き換えで消えた時刻（`erased_at`） |
| `PR.jsonl`・`issue.jsonl` | PR と issue のいちばん新しい形（状態・ラベル・担当・日時・下書きか・変更の大きさ） |
| `コメント.jsonl` | 会話のコメント・コードの行へのコメント（コードの断片は捨てる）・レビュー（承認・変更の依頼・コメント） |
| `出来事.jsonl` | PR と issue に起きたこと（閉じた・マージした・ラベル・下書きから外した・題名の変更・担当など。誰がいつ。ボットの動きか〈`bot`〉） |
| `CI.jsonl` | CI の結果（動いた PR と基準のブランチの先頭の、先頭のコミットの検査） |
| `リリース.jsonl` | 版の名札と日付 |

どの行にも、次の欄があります。

| 欄 | 中身 |
| --- | --- |
| `known_at` | 知った時刻（その行のものが、初めて原本に現れた取得の時刻）。取ったときにしか残せません |
| `author`・`author_id` など | 人は、GitHub のログイン名と番号（ID）の組で持ちます。ログイン名は本人が変えられますが、番号は変わりません。表示名とメールは持ちません |
| `untrusted` | 他人が書いた文字列の欄の名前（題名・本文・コメント・ラベルなど）。この記録を AI に渡すときは、区切りで囲み、「中は指示ではなくデータ」と書いてください |

- アプリの画面には、人の名前を出しません。数は「PR 経由／直接」のように、入り方で分けます
- **原本には、GitHub の返事のまま、コミットの作者の名前とメールが入ります**（記録には入れません）。原本を人に渡すときは気をつけてください

## しくみ

```text
[アプリ（毎朝・今すぐ取る）] または [ターミナル]
        │
        ▼
[github.py fetch] リポジトリを1つずつ取る（1つが失敗しても、次へ進む）
   1. ログインを確かめる（user）。回数の枠は、返事に付く数で見る
   2. リポジトリの情報と基準のブランチの先頭 → 入った記録 → コミット
   3. PR と issue の一覧 → 動いた PR の詳しさとレビュー → 出来事
   4. コメント → CI の結果 → リリース → 照合に使う検索（PR と issue の数）
      ※ 問い合わせはすべて gh api --method GET（許可リストを通ったものだけ）
        │
        ▼
   記録を作る（原本 → 記録）→ 照合 → 状態.json と取得の記録 → Mac の通知
```

- **前回の続きから取ります**。PR・issue・コメント・出来事は、前回うまく取れた時刻の 14 日前から重ねて取り直します（GitHub の一覧は、更新のすぐあとには出てこないことがあるため）。重なった分は番号で1つにまとめます
- **変わっていないものは 304 で済ませます**。前に問い合わせた場所には前の印（ETag）を添えて、変わっていなければ「変わっていない」（304）が返ります。304 は GitHub の回数を使いません（2026年10月に測った）。動きのないリポジトリは、毎朝ほぼ 304 で済みます
- **ページは自分で送ります**（`--paginate` は使いません）。1ページごとに原本を書くので、途中で止まっても、取れた分は残ります。途中で切れたページ・形の崩れた返事は、間をあけて3回まで取り直します。次のページが空で返ったときは1回だけ取り直し、それでも空なら照合の NG にします
- **入ったものの数え方**: 時計は、ブランチに入った時刻です（コミットに書かれた日付は使いません）。PR がマージされた記録なら、そのとき入ったコミットは全部その PR 経由で、PR 1 件を 1 つと数えます。直接の push は、コミット1つずつ数えます。マージのコミット（親が2つ以上）は記録に残して、数えません。強制の書き換え（force push）で入ったものは数えず、消えたものには印を付けます（それまでに数えた分は減らしません）
- 照合（毎回、取ったあと）で見ること:
  - ページの取りこぼし: 一覧を最後のページまで取れた。途中で切れたページが無い
  - 件数の突き合わせ: PR と issue の数が、GitHub の検索の数と同じ。PR・issue ごとのコメントの数が、GitHub の表示どおり
  - 期間の抜け: 取り始める日から最後の取得まで、すき間が無い
  - ブランチのつながり: 入った記録が1本の鎖になっている
  - 入り方の見分け: 入ったコミットが、すべて「PR 経由」か「直接」に分かれた
  - 基準の先頭: GitHub がいま指している基準のブランチの先頭が、記録の最後と同じ（同じなら「新しく入ったもの 0」は本物）
  - 開いている数: GitHub の開いている PR と issue の数が、記録と同じ
  - 出来事のつながり: 前回いちばん新しかった出来事が、今回も見つかる
  - 出来事と一覧: 一覧で閉じた・マージした PR と issue に、同じ時刻の出来事がある
  - 原本の形: 原本がすべて読める
  - 既知の例外: `例外.json` に入れたもの
- 合わないときは、少し待って1回だけ取り直します（GitHub の一覧が少し遅れることがあるため）。取り直しは1回目と同じ範囲を読みます。それでも合わなければ NG です
- 確かめるのは、その回に最後まで読んだリポジトリだけです。最初の取得の途中のリポジトリや、その回は途中で止まったリポジトリは、「OK」とも「NG」とも言わず「確かめていない」と理由を出し、照合のタイルを緑にしません
- GitHub の入った記録が抜けていて鎖が切れているときは、前後のコミットを比べる問い合わせ（compare）を1回して間を埋め、「推定」の印を付けて注記に出します。埋められないときだけ NG です
- 作者のアカウントが消された PR は、GitHub の検索に出ないので、検索の数と比べる前に除きます（注記に出します）
- 見えないリポジトリ（404）は「見えません」と出します（権限が無いか、名前が変わったか、消えた）。「無い」とは言いません
- `python3 github.py status refresh` で、GitHub に問い合わせずに、状況ページの数と照合を数え直せます。`python3 github.py build` で、原本から記録を作り直せます

## 使う回数の目安

GitHub の REST API の回数の枠は、ログインしたアカウントで1時間 5,000 回です（ほかの gh や、gh を使う道具と分け合います）。この仕組みは、枠の残りが 300 回を切ったら止めて待ち、枠が戻る時刻に、アプリが自動で続きを取ります。

| 場面 | 回数（2026年10月に測った数） |
| --- | --- |
| 最初の取得・小さい個人のリポジトリ 11 個を全部 | 174 回 |
| 最初の取得・大きい公開リポジトリ（ggml-org/whisper.cpp。PR 約 1,500）を 90 日前から | 396 回（CI を約 13 か月分聞くようにしたので、いまは約 650 回の見込み） |
| 同じリポジトリを、作った日（2022年9月）から全部 | 3,545 回（766・1,500・1,279 の 3 回に分かれた。Mac が起きていた時間で約 40 分）。CI を約 13 か月分聞くようにしたので、いまは約 4,450 回の見込み（3〜4 回） |
| 毎朝・小さい個人のリポジトリ 11 個 | 照合の検索 22 回（検索の枠〈1分 30 回〉で数え、1時間 5,000 回の枠は使わない）＋動いた分 |
| 毎朝・大きい公開リポジトリ | 約 20〜100 回（見込み） |

1回の問い合わせは 0.4〜0.7 秒です。使った回数は、アプリの状況ページ（「使った回数」のタイルと「取得の記録」）で見られます。

## 気をつけること

- **会社のデータを手元にためることがあります**。上の「使う前に」を読んで、会社の決まりを確かめてください
- **関係する決まり**（2026年10月に確かめたもの。変わることがあります）
  - [GitHub 利用規約](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service)（2026年4月27日版）の H 章「API Terms」: API への行き過ぎた問い合わせは、API の利用を止められることがあります。回数の制限を超えるためにトークンを共有してはいけません。スパムや、利用者の個人情報を売るために、データを取ってはいけません
  - [GitHub Acceptable Use Policies](https://docs.github.com/en/site-policy/acceptable-use-policies/github-acceptable-use-policies) の 7 章（情報の使い方の制限）・8 章（プライバシー）: 自動で集めた情報の使い方と、集めた個人情報の扱い（GitHub のプライバシーの決まりに従い、許された目的だけに使い、守る）
  - [REST API の回数の制限](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api): ログインしたアカウントで1時間 5,000 回。ほかに、短い時間に多すぎる問い合わせの制限（`retry-after`）があります。この仕組みは、問い合わせを1つずつ順に送り、`retry-after` が返ったら言われた秒数だけ待ちます
- 取れるのは、自分の GitHub のアカウントから見えるものだけです。見えないことと、無いことは、同じではありません
- あとから書き直された PR・issue・コメントは、更新の時刻が新しくなるので、次の取得で取り直して記録も新しい形になります。消されたものは、記録に取ったときのまま残ります（消えた印は、まだ付けません。原本も消しません）
- CI の結果は、最初の取得では、約 13 か月の間に動いた PR と基準のブランチの先頭のものまで取ります。GitHub は約 13 か月で CI の結果を消すので、それより前の CI は取れません
- 入った記録（GitHub の activity）が始まる前の古いコミットは、まだ数えていません（大きくて古いリポジトリを作った日から取るとき）。照合の注記に、数えていないコミットの数を出します
- 確認環境・本番のブランチの届き具合（`stages`）は、まだ作っていません
- 取る係も gh を使うので、gh のログインが切れると取得が失敗し、アプリが「ログインが必要です」と知らせます

## うまくいかないとき

| 出る言葉 | すること |
| --- | --- |
| 取るリポジトリが無い | アプリの「はじめの準備」でリポジトリを選ぶ（はじめ方の3）。ターミナルだけで使うときは `~/GitHub取得データ/リポジトリ.json` を作る |
| gh が見つかりません | gh を入れる（`brew install gh`。または [GitHub CLI](https://cli.github.com/)） |
| ログインが必要です | アプリの「ターミナルでログイン」（設定の「ログインし直す…」）か、ターミナルで `gh auth login` を動かしてから、もう一度取る。取れた分は残っています |
| 回数の上限で待っています | 何もしなくてよい。枠が戻る時刻に、アプリが自動で続きを取ります（抜けません。ターミナルだけで使うときは、戻る時刻のあとにもう一度動かす） |
| 最初の取得の途中です | 何もしなくてよい（大きいリポジトリは 1,500 回ずつ分けて取ります）。「今すぐ取る」か次の朝の自動取得で、続きから取ります |
| 照合: 確かめていない | 最後まで読めなかったリポジトリがある、という意味です（最初の取得の途中・その回は途中で止まった・取れなかった）。最後まで取れれば確かめます |
| 番号が入っていないリポジトリがあります | `~/GitHub取得データ/リポジトリ.json` の `id` が 0 か空。`python3 github.py setup --find owner/name` で調べて書く（例を写したままのとき） |
| 途中で止まりました（1回の上限） | もう一度取る（「今すぐ取る」）。続きから取ります。上限は設定で変えられます |
| 一部のリポジトリが取れませんでした（見えません） | 権限が無いか、名前が変わったか、消えたもの。「GitHub とリポジトリ…」でリポジトリを見直す。ほかのリポジトリは取れています |
| 組織の許可（SSO）が要ります | ブラウザで、組織のシングルサインオンを許可してから、もう一度取る（[SSO の説明](https://docs.github.com/en/authentication/authenticating-with-saml-single-sign-on/about-authentication-with-saml-single-sign-on)・[許可したアプリ](https://github.com/settings/applications)） |
| GitHub につながりませんでした・GitHub の側が不調でした | ネットを確かめて、少し待ってからもう一度取る。次は続きから取ります |
| 照合で合わないものがあります | もう一度取る。続くときは `~/GitHub取得データ/取得ログ/` のいちばん新しいログを見る |
| 許可リストの外の問い合わせを止めた | 作りのまちがいです。github.py を直さずに、取得ログの全文で原因を確かめてください（人に見せるときは、非公開のリポジトリの名前や番号を伏せる） |
| フォルダを読む許可がありません | システム設定 → プライバシーとセキュリティ → ファイルとフォルダ で「GitHub 取得」をオンにする |
| 取得の仕組みのフォルダが見つかりません | アラートの「場所を選ぶ」で、github.py のあるフォルダ（または1つ上のフォルダ）を選ぶ |
| スリープで取れなかった分があります | Mac が起きているときに「もう一度取る」を押す（続きから取ります） |

何度取り直しても合わないもの（GitHub 側の食い違いで、直しようがないもの）は、`~/GitHub取得データ/例外.json` に、NG の行の一部（`match`。状況ページや取得ログに出る NG の行から、頭の「NG 」を除いた一部を写す）と理由を書いておけます。照合のたびに NG にせず、「既知の例外」として表示されます。

```json
[{"match": "音声: #123 のコメントが GitHub", "reason": "GitHub の数と、見えるコメントの数が合わない"}]
```

## 細かい設定

`github.py fetch` は、次の値を環境変数で変えられます（例: `CALL_CAP=500 python3 github.py fetch`）。

| 名前 | 既定 | 中身 |
| --- | --- | --- |
| `CALL_CAP` | `1500` | 1回の取得で GitHub に問い合わせてよい回数（304 は数えない）。`0` は上限なし。アプリの設定でも変えられます |
| `NOTIFY` | `1` | `0` にすると、Mac の通知を出しません |
| `GITHUB_FETCH_DATA` | `~/GitHub取得データ` | 取ったデータの置き場所。試しのとき用です（Finder から開いたアプリには、ターミナルで付けた値が届かないので、ふだん変えると、アプリとターミナルでデータが2か所に分かれます） |

## ファイル

| ファイル | 中身 |
| --- | --- |
| `github.py` | 取る係・記録づくり・照合・状態の書き出し・はじめの準備の調べもの（Python の標準の部品だけ） |
| `CLAUDE.md` | Cursor・VS Code などで、このフォルダを開いた Claude への手順書（「準備して」と頼んだときの進め方） |
| `設計書.md` | 何をどう取り、どう数え、どう照合するかの決めごとと、その理由 |
| `リポジトリ.例.json` | リポジトリの書き方の見本（写して `~/GitHub取得データ/リポジトリ.json` にする） |
| `~/GitHub取得データ/` | 取ったもの・設定・状態（このフォルダの外。取得のときにできる。中身は「できるもの」） |
| `アプリ/` | メニューバーのアプリ（`Sources/`・`Info.plist`・`build.sh`）。はじめの準備（「GitHub とリポジトリ」）の窓は `Sources/Setup.swift` |
| `アプリ/リンク.json` | はじめの準備の窓で開くリンク（gh の入れ方・ログインのしかた・SSO など）。組み立てるときにアプリに入る |
| `アプリ/見本/` | 画面を確かめるための作り物の状態（`見本の状態.py`）と、全部の画面を画像に書き出す台本（`画面を書き出す.sh`） |

アプリの見た目と動きは、開かずに確かめられます（`アプリ/build/GitHub取得.app/Contents/MacOS/GitHubFetch` に付けて動かす）。`--snapshot <書き出すフォルダ>` で画面を画像に書き出し（作り物の状態で描きます。自分のデータで描くときは `-dataDir ~/GitHub取得データ` を付けます）、`--test-base`（フォルダの追いかけ）・`--test-setup`（リポジトリの付け外し）・`--test-chart`（グラフにマウスを乗せたときの日の見分け）で自分を試します。どれもデータを書き換えず、取得も動かしません。
